## What system/approach is used

This repository uses **npm** as the package manager for Node.js/TypeScript dependencies, with a standard `package.json` manifest and a committed `package-lock.json` lockfile (lockfileVersion 3). It also uses **Prisma CLI** (`prisma`) as a dev dependency to manage database schema migrations and client generation, and a custom **skills lockfile** (`skills-lock.json`) to pin AI agent skill definitions sourced from GitHub.

There is no vendoring of npm packages — all third-party code is resolved at install time from the public npm registry. No private npm registry, `.npmrc`, or `npm_config_registry` overrides were found in the repository.

## Key files and packages

- `package.json` — declares runtime and dev dependencies; pinned major versions via caret ranges (`^7.9.1`, `^0.45.1`, `^11.0.2`, `^16.3.2`, etc.). Notable runtime deps include `next`, `react`/`react-dom`, `@prisma/client`, `@prisma/adapter-pg`, `pg`, `argon2`, `google-auth-library`, `lucide-react`, `puppeteer`, `react-markdown`. Dev deps include `prisma`, `tailwindcss`, `eslint`, `typescript`, `@types/*`.
- `package-lock.json` — full deterministic lockfile generated by npm, recording exact resolved versions, integrity hashes, and transitive dependency trees for every package listed in `package.json`.
- `prisma/schema.prisma` — Prisma data model that drives `prisma generate` to produce the typed `@prisma/client`; this is the source-of-truth for the ORM layer.
- `prisma/migrations/*.sql` + `prisma/migrations/migration_lock.toml` — version-controlled SQL migration files managed by Prisma Migrate; the lockfile pins the provider (`postgresql`) so migrations stay reproducible across environments.
- `skills-lock.json` — pins nine Prisma-related AI agent skills (e.g., `prisma-cli`, `prisma-client-api`, `prisma-compute`, `prisma-database-setup`, `prisma-driver-adapter-implementation`, `prisma-mongodb-upgrade`, `prisma-postgres`, `prisma-postgres-setup`, `prisma-upgrade-v7`) fetched from the `prisma/skills` GitHub source, each with a `computedHash` to ensure deterministic installs.

## Architecture and conventions

- **Single-package workspace**: The repo is a single Next.js application with one `package.json`; there are no nested workspaces or monorepo structures, so dependency resolution is flat.
- **Versioning strategy**: Runtime dependencies use caret (`^`) ranges to allow patch/minor updates while staying on compatible major versions (e.g., `next: 16.3.2`, `prisma: ^7.9.1`, `@prisma/client: ^7.9.1`). Dev dependencies similarly use caret ranges. This balances stability with access to newer features.
- **Lockfile-first reproducibility**: `package-lock.json` is committed alongside `package.json`, ensuring that `npm ci` produces an identical dependency tree across machines and CI. The same philosophy applies to Prisma migrations via `migration_lock.toml`.
- **Separation of concerns between app deps and tooling**: Database access is split between `@prisma/client` (generated ORM) and `pg` (raw driver), with `@prisma/adapter-pg` bridging them. Authentication uses `argon2` for password hashing and `google-auth-library` for OAuth flows. UI icons come from `lucide-react`; markdown rendering from `react-markdown`.
- **Skills as a separate dependency surface**: AI agent capabilities are not npm packages but Markdown-based skills pulled from GitHub and pinned via `skills-lock.json`, keeping them decoupled from the application's npm dependency graph.

## Conventions and constraints

- All third-party libraries are declared explicitly in `package.json` under `dependencies` or `devDependencies`; there are no implicit runtime imports without a corresponding manifest entry.
- Transitive dependencies are fully captured in `package-lock.json`; developers should update dependencies via `npm update` / `npm install` rather than editing the lockfile manually.
- Prisma schema changes must go through `prisma/schema.prisma` followed by `prisma migrate` to generate new SQL migrations under `prisma/migrations/`; the `migration_lock.toml` enforces that the database provider stays PostgreSQL.
- Skills are versioned by content hash (`computedHash`) in `skills-lock.json`, so any change to a skill's source material will be detected and require re-locking.
- No private registry, scoped package configuration, or vendored node_modules exists in the repository — all packages resolve against the default npm registry.
